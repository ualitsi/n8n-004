Resumen

Esta práctica se centra en la fiabilidad y la mantenibilidad de los flujos de trabajo. Se introduce el manejo de errores mediante el Error Trigger (un flujo de trabajo dedicado que se activa cuando otro falla) y el nodo Stop and Error (para detener deliberadamente un flujo cuando los datos no cumplen las condiciones esperadas). Además, se aborda la modularidad a través de sub-flujos de trabajo con el par de nodos Execute Workflow y Execute Workflow Trigger, aplicando el principio DRY a la automatización. A lo largo de la sesión se construye un sistema de tres flujos de trabajo (principal, sub-flujo y manejador de errores) y se resuelven varios ejercicios de complejidad creciente.

Objetivos

  • Diseño de Flujos de Trabajo Resilientes.

  • Manejo de Errores Centralizado.

  • Implementación de Sub-Flujos de Trabajo.

1. Objetivos de la Práctica

A medida que los flujos de trabajo aumentan en complejidad y se vuelven críticos para los procesos de negocio, su fiabilidad y mantenibilidad se convierten en prioridades. Esta práctica introduce dos de los conceptos más importantes para la construcción de automatizaciones a nivel de producción: el manejo de errores y la modularidad a través de sub-flujos de trabajo. Se aprenderá a diseñar sistemas que no solo ejecutan tareas, sino que también reaccionan de forma inteligente a los fallos y están estructurados de manera limpia y reutilizable.

Al finalizar esta sesión, el estudiante habrá desarrollado las siguientes competencias:

  • Diseño de Flujos de Trabajo Resilientes: Comprender la importancia del manejo de errores y diseñar sistemas que puedan detectar, registrar y notificar fallos de ejecución.

  • Manejo de Errores Centralizado: Implementar un flujo de trabajo de manejo de errores dedicado utilizando el Error Trigger para capturar y procesar fallos de otros flujos de trabajo de manera centralizada.

  • Control de Errores Proactivo: Utilizar el nodo Stop and Error para detener deliberadamente un flujo de trabajo y lanzar un error personalizado cuando se cumplen ciertas condiciones (por ejemplo, validación de datos fallida).

  • Principios de Modularidad (DRY): Aplicar el principio "Don’t Repeat Yourself" (No te repitas) a la automatización de flujos de trabajo mediante la creación de lógica reutilizable.

  • Implementación de Sub-Flujos de Trabajo: Construir y ejecutar flujos de trabajo modulares utilizando el par de nodos Execute Workflow (para llamar a un sub-flujo) y Execute Workflow Trigger (para iniciar un sub-flujo), permitiendo la encapsulación de lógica de negocio.

2. Fundamentos Teóricos

2.1. Manejo de Errores: Construyendo Flujos de Trabajo Robustos

Hasta ahora, si un nodo en nuestro flujo de trabajo fallaba (por ejemplo, una API no estaba disponible o los datos de entrada eran incorrectos), la ejecución simplemente se detenía. En un entorno de producción, esto es inaceptable. Necesitamos un mecanismo para detectar estos fallos y actuar en consecuencia, ya sea para reintentar la operación, notificar a un administrador o registrar el incidente para su posterior análisis.

n8n proporciona un sistema de manejo de errores elegante y potente basado en un flujo de trabajo especial.

  • El Error Trigger: Este es un tipo especial de disparador que, en lugar de reaccionar a un horario o a un webhook, se activa cuando otro flujo de trabajo falla. Un flujo de trabajo que comienza con un Error Trigger se conoce como un "flujo de trabajo de errores" (Error Workflow).

  • Configuración del Flujo de Trabajo de Errores: En la configuración de cualquier flujo de trabajo (en el menú de tres puntos > Settings), hay una opción llamada "Error Workflow". Aquí, se puede seleccionar el flujo de trabajo que contiene el Error Trigger. Una vez configurado, si el flujo de trabajo principal falla, n8n detendrá su ejecución y activará inmediatamente el flujo de trabajo de errores designado.

  • Datos del Error: El Error Trigger no se activa en vacío. Proporciona un objeto JSON rico en información sobre el fallo, que incluye:

    • execution.error.message: El mensaje de error específico.

    • execution.lastNodeExecuted: El nombre del nodo que falló.

    • workflow.name: El nombre del flujo de trabajo que falló.

    • execution.url: Un enlace directo a la ejecución fallida en la interfaz de n8n para una depuración rápida. Esto permite que el flujo de trabajo de errores envíe notificaciones muy detalladas (por ejemplo, "El flujo 'Procesar Pedidos' ha fallado en el nodo 'Actualizar Base de Datos' con el error: 'Conexión rechazada'").

  • El Nodo Stop and Error: A veces, un flujo de trabajo no falla debido a un error técnico, sino porque los datos no cumplen con las condiciones de negocio esperadas. Por ejemplo, una API devuelve un producto sin precio. El flujo podría continuar, pero podría causar problemas más adelante. El nodo Stop and Error permite manejar esto de forma proactiva. Cuando un ítem llega a este nodo, la ejecución del flujo de trabajo se detiene inmediatamente y se considera un fallo. Esto activará el flujo de trabajo de errores. Se puede configurar un mensaje de error personalizado, lo que permite un control total sobre por qué y cómo falla un flujo de trabajo.

2.2. Modularidad: Sub-Flujos de Trabajo (Sub-Workflows)

A medida que se construyen más automatizaciones, se encontrarán patrones de lógica que se repiten. Por ejemplo, el proceso de registrar un evento en una hoja de Google Sheets y luego enviar una notificación a Slack puede ser necesario en muchos flujos de trabajo diferentes. Copiar y pegar estos nodos en cada flujo es ineficiente y propenso a errores. Si se necesita cambiar la lógica de notificación, habría que actualizarla en todos los lugares donde se copió.

n8n resuelve este problema con los sub-flujos de trabajo, que permiten encapsular lógica reutilizable. Este sistema se basa en dos nodos que trabajan en conjunto:

  • Execute Workflow Trigger: Este nodo actúa como el punto de entrada para un sub-flujo de trabajo. En lugar de un Manual Trigger o Schedule Trigger, un flujo de trabajo que comienza con este disparador esperará a ser llamado por otro flujo de trabajo. Puede ser configurado para recibir datos del flujo de trabajo que lo llama.

  • Execute Workflow: Este nodo se coloca en el flujo de trabajo "principal" (o "padre"). Se configura para apuntar a un sub-flujo de trabajo (el que tiene el Execute Workflow Trigger). Cuando la ejecución llega a este nodo, el flujo principal se pausa, pasa los datos de entrada al sub-flujo, y espera a que el sub-flujo termine. Una vez que el sub-flujo ha completado su ejecución, devuelve sus datos de salida al nodo Execute Workflow, y el flujo principal reanuda su ejecución.

Este patrón es increíblemente poderoso. Permite crear una "biblioteca" de flujos de trabajo de utilidad (como "EnviarNotificacion", "ValidarDatosDeUsuario", "GenerarInformePDF") que pueden ser llamados desde cualquier otro flujo de trabajo, promoviendo un diseño limpio, modular y fácil de mantener.

3. Desarrollo del Flujo de Trabajo Guiado

En esta práctica, construiremos un sistema de tres flujos de trabajo: un flujo principal que procesa una lista de URLs de imágenes, un sub-flujo que intenta descargar cada imagen, y un flujo de errores que registra cualquier fallo en el proceso en una hoja de Google Sheets.

3.1. Paso 1: Crear el Flujo de Trabajo de Errores

Este será nuestro "centro de monitoreo".

  1. Cree un nuevo flujo de trabajo y nómbrelo "Manejador de Errores".

  2. Añada el Error Trigger como primer nodo. No requiere configuración.

  3. Prepare una hoja de Google Sheets con las cabeceras: Timestamp, Workflow Fallido, Nodo Fallido, Mensaje de Error, URL de Ejecución.

  4. Conecte un nodo Google Sheets al Error Trigger.

  5. Configure el nodo Google Sheets con la operación Append Row para que escriba en la hoja que acaba de crear. Mapee los datos del Error Trigger:

    • Timestamp: {{ $now }}

    • Workflow Fallido: {{ $json.workflow.name }}

    • Nodo Fallido: {{ $json.execution.lastNodeExecuted }}

    • Mensaje de Error: {{ $json.execution.error.message }}

    • URL de Ejecución: {{ $json.execution.url }}

  6. Guarde y active este flujo de trabajo. A diferencia de los sub-flujos (Paso 2), el flujo de errores sí debe estar activado para poder capturar los fallos de los demás flujos.

3.2. Paso 2: Crear el Sub-Flujo de Trabajo "Descargador de Imágenes"

Esta será nuestra pieza de lógica reutilizable.

  1. Cree un nuevo flujo de trabajo y nómbrelo "Sub-flujo: Descargador de Imágenes".

  2. Añada el Execute Workflow Trigger como primer nodo. Este nodo recibirá la URL de la imagen a descargar.

  3. Conecte un nodo HTTP Request al disparador.

  4. Configure el HTTP Request:

    • URL: {{ $json.imageUrl }} (Asumimos que el flujo principal enviará un objeto con esta clave).

    • Options > Response Format: File. Esto le dice a n8n que espere datos binarios como respuesta.

  5. (Opcional) Conecte un nodo Google Drive o Read/Write Files from Disk para guardar la imagen descargada.

  6. Guarde este flujo de trabajo. No es necesario activarlo: los sub-flujos llamados mediante el nodo Execute Workflow se ejecutan aunque estén desactivados. Anote su ID (visible al final de la URL del navegador al editar el flujo) para el siguiente paso.

3.3. Paso 3: Crear el Flujo de Trabajo Principal

Este flujo orquestará todo el proceso.

  1. Cree un nuevo flujo de trabajo y nómbrelo "Procesador Principal de Imágenes".

  2. Configurar el Manejador de Errores:

    • Vaya a Options > Settings.

    • En el desplegable Error Workflow, seleccione su flujo "Manejador de Errores".

    • Guarde la configuración.

  3. Simular Datos de Entrada:

    • Añada un Manual Trigger.

    • Conecte un nodo Edit Fields (Set) para crear una lista de URLs, incluyendo una que sea deliberadamente incorrecta para forzar un error.

      • Name: imageUrls

      • Value (Expression):

        [
  {"imageUrl": "https://placedog.net/320/240"},
  {"imageUrl": "https://dummyimage.com/320x240"},
  {"imageUrl": "https://esta-url-no-existe.xyz/imagen.jpg"}
]

      • Asegúrese de que el tipo de dato sea JSON.

  4. Procesar la Lista:

    • Conecte un nodo Split Out para separar la lista en ítems individuales.

    • Field To Split Out: imageUrls

  5. Llamar al Sub-Flujo:

    • Conecte un nodo Execute Workflow al Split Out.

    • Workflow: Seleccione el sub-flujo "Sub-flujo: Descargador de Imágenes" en el desplegable (o introduzca el ID que anotó en el Paso 2).

    • El nodo pasará automáticamente el ítem actual ({ "json": { "imageUrl": "…​" } }) como entrada al sub-flujo.

  6. Ejecutar y Verificar:

    • Ejecute el flujo de trabajo principal manualmente.

    • La ejecución se mostrará como fallida. Al inspeccionarla, verá que el nodo Execute Workflow que intentó procesar la URL incorrecta está marcado en rojo.

    • Abra su hoja de Google Sheets. Debería haber una nueva fila registrando el error, con todos los detalles del fallo: el nombre del flujo principal, el nodo Execute Workflow como el que falló, y el mensaje de error del HTTP Request del sub-flujo (por ejemplo, "ENOTFOUND").

4. Ejercicios Propuestos

4.1. Ejercicio 1: Notificación de Errores Mejorada (Dificultad: Baja)

Objetivo: Mejorar el "Manejador de Errores" para que, además de registrar el error en Google Sheets, envíe una notificación por correo electrónico.

Requisitos:

  1. Cree una credencial SMTP en n8n. Para las pruebas puede usar un servicio de correo de pruebas gratuito (como Mailtrap o Brevo) o una cuenta de Gmail con una contraseña de aplicación.

  2. Modifique el flujo de trabajo "Manejador de Errores".

  3. Añada un nodo Send Email (o un nodo de Slack/Telegram si lo prefiere) después del nodo de Google Sheets y seleccione la credencial SMTP.

  4. Configure el nodo para enviar un correo con un asunto claro (ej. "¡Alerta de Error en n8n!").

  5. En el cuerpo del correo, incluya la misma información que se registra en Google Sheets (nombre del flujo, nodo, mensaje y URL), utilizando las expresiones del Error Trigger.

  6. Fuerce un error desde el flujo principal (ejecútelo con la URL incorrecta) y verifique que recibe el correo con todos los detalles.

4.2. Ejercicio 2: Sub-Flujo de Validación de Datos (Dificultad: Media)

Objetivo: Crear un sub-flujo de trabajo reutilizable que valide la estructura de los datos de un producto y lance un error si faltan campos clave.

API a utilizar: Fake Store API (https://fakestoreapi.com/products/1)

Requisitos:

  1. Cree un sub-flujo llamado "Sub-flujo: Validador de Productos" que comience con un Execute Workflow Trigger.

  2. Dentro de este sub-flujo, use un nodo IF con dos condiciones combinadas con el operador AND:

    • {{ $json.title }} → tipo String → operación is not empty

    • {{ $json.price }} → tipo Number → operación exists

  3. En la rama true (producto válido), añada un nodo Edit Fields (Set) que cree un campo validacion con el valor OK. Este será el resultado que devuelva el sub-flujo al flujo principal.

  4. En la rama false (falta alguno de los campos), conecte un nodo Stop and Error con el mensaje "Validación fallida: Faltan campos de producto obligatorios".

  5. Cree un flujo principal que llame a la Fake Store API para obtener el producto 1.

  6. (Para forzar el error) Añada un nodo Edit Fields (Set) después de la llamada a la API para eliminar el campo price del objeto: añada un campo llamado price y cambie su Tipo a Remove.

  7. Llame al sub-flujo "Validador de Productos" con el nodo Execute Workflow.

  8. Asegúrese de que el flujo principal tiene configurado el "Manejador de Errores" y verifique que el error personalizado se registra correctamente en su hoja de Google Sheets.

  9. Pregunta de reflexión: ¿Qué pasaría si, en lugar del nodo Stop and Error, la rama false simplemente no conectara ningún nodo? Investigue la diferencia entre que un flujo falle y que termine devolviendo ítems vacíos.

4.3. Ejercicio 3: Orquestador de Tareas Dinámicas (Dificultad: Alta)

Objetivo: Crear un flujo principal que decide qué tarea realizar y llama al sub-flujo apropiado para ejecutarla.

APIs a utilizar: * Bored API para actividades: https://bored-api.appbrewery.com/random * Public Holidays API: https://date.nager.at/api/v3/PublicHolidays/2026/ES

Requisitos:

  1. Cree dos sub-flujos simples:

    • "Sub-flujo: Obtener Actividad": Llama a la Bored API y devuelve la actividad.

    • "Sub-flujo: Obtener Festivos": Llama a la API de festivos y devuelve la lista de festivos.

  2. Cree un flujo principal que comience con un Manual Trigger.

  3. Añada un nodo Edit Fields (Set) que cree una variable de control: un campo tarea con el valor actividad.

  4. Use un nodo Switch que evalúe el campo {{ $json.tarea }}.

    • Si tarea es "actividad", conecte un nodo Execute Workflow que llame al sub-flujo "Obtener Actividad".

    • Si tarea es "festivos", conecte un nodo Execute Workflow que llame al sub-flujo "Obtener Festivos".

  5. Conecte un nodo Merge en modo Append a las salidas de ambos nodos Execute Workflow para consolidar el resultado.

  6. Añada un nodo Edit Fields (Set) final para verificar la salida. Pruebe el flujo cambiando el valor de la variable tarea a "festivos" y vuelva a ejecutarlo para confirmar que se llama al sub-flujo correcto.

  7. Pregunta de reflexión: Observe que el sub-flujo de festivos devuelve un único ítem que contiene un array de 32 festivos, mientras que el de actividades devuelve un único objeto. ¿Cómo modificaría el flujo para que la salida final contuviera un ítem por festivo? (Pista: Split Out dentro del sub-flujo).

4.4. Ejercicio 4: Sub-Flujo Notificador Reutilizable (Dificultad: Alta)

Objetivo: Aplicar el principio DRY creando un sub-flujo de notificación que centralice el registro de eventos, y llamarlo desde dos flujos de trabajo diferentes.

Requisitos:

  1. Cree un sub-flujo llamado "Sub-flujo: Notificador" que comience con un Execute Workflow Trigger. El sub-flujo recibirá un objeto con dos campos: mensaje (texto) y nivel ("INFO" o "ERROR").

  2. Dentro del sub-flujo, use un nodo Switch sobre el campo {{ $json.nivel }} para enrutar a dos nodos Google Sheets:

    • Rama "INFO": escribe en una hoja llamada Eventos.

    • Rama "ERROR": escribe en una hoja llamada Alertas.

    • Ambas hojas deben incluir las columnas Timestamp ({{ $now }}), Nivel y Mensaje.

  3. Modifique el flujo "Manejador de Errores" (de la práctica guiada) para que, además de escribir en su hoja, llame al sub-flujo "Notificador" con nivel = ERROR y un mensaje construido a partir de los datos del error (por ejemplo, {{ "Fallo en " + $json.workflow.name + ": " + $json.execution.error.message }}).

  4. Modifique el flujo principal "Procesador Principal de Imágenes" para que, al final, llame al sub-flujo "Notificador" con nivel = INFO y un mensaje como Procesamiento de imágenes completado.

  5. Ejecute ambos flujos y verifique que los eventos aparecen en las hojas correctas.

  6. Pregunta de reflexión: Si mañana necesita añadir un canal de notificación nuevo (por ejemplo, Slack), ¿cuántos flujos de trabajo tendría que modificar gracias a este diseño? ¿Y cuántos habría tenido que modificar si cada flujo escribiera sus notificaciones por su cuenta?

4.5. Ejercicio 5: Monitor de Salud de APIs (Dificultad: Muy Alta)

Objetivo: Crear un flujo de trabajo programado que comprueba periódicamente el estado de varias APIs externas, de modo que un fallo individual no detenga el resto de comprobaciones, y registra el resultado de cada una en Google Sheets.

APIs a comprobar: * Fake Store API: https://fakestoreapi.com/products/1 * JokeAPI: https://v2.jokeapi.dev/joke/Programming?type=single * Nager.Date: https://date.nager.at/api/v3/PublicHolidays/2026/ES

Requisitos:

  1. Cree un sub-flujo llamado "Sub-flujo: Comprobar API" que comience con un Execute Workflow Trigger.

    • El sub-flujo recibirá un objeto con un campo url.

    • Dentro, use un nodo HTTP Request con la URL {{ $json.url }}.

    • Añada un nodo Edit Fields (Set) que cree un campo estado con el valor OK (solo se alcanzará si la petición fue exitosa).

  2. Cree un flujo principal que comience con un Schedule Trigger que se ejecute cada hora.

  3. Añada un nodo Edit Fields (Set) (con tipo de dato JSON) que cree una lista apis con las tres URLs.

  4. Use un Split Out sobre apis para obtener un ítem por API.

  5. Llame al sub-flujo "Comprobar API" con un nodo Execute Workflow.

    • Punto clave: En la pestaña Options del nodo Execute Workflow, active la opción On Error y selecciónela como Continue. Así, si una API falla, el flujo continuará con la siguiente en lugar de detenerse.

  6. Añada un nodo IF que compruebe si el campo {{ $json.estado }} es igual a OK.

    • Rama true: escriba en la hoja Salud_OK de un Google Sheet (columnas URL y Hora ({{ $now }})).

    • Rama false: escriba en la hoja Salud_Fallo (mismas columnas).

  7. Configure el "Manejador de Errores" como flujo de errores del monitor, por si algún fallo no esperado (por ejemplo, en el propio nodo de Google Sheets) detiene la ejecución.

  8. Active el flujo y espere a la siguiente ejecución programada para verificar los resultados en las hojas.

  9. Pregunta de reflexión: ¿Por qué es importante combinar la opción On Error: Continue con el flujo de errores? ¿Qué tipo de fallos captura cada mecanismo?

5. Conclusiones y Avance de la Próxima Práctica

En esta práctica, hemos elevado nuestras habilidades de diseño de automatización a un nuevo nivel, centrándonos en la robustez y la reutilización. Ahora somos capaces de construir sistemas que no solo funcionan en condiciones ideales, sino que también gestionan los fallos de manera predecible. La modularización mediante sub-flujos de trabajo nos permite crear soluciones más limpias, escalables y fáciles de mantener.

En la próxima práctica, nos adentraremos en el núcleo de la persistencia y la comunicación de datos en arquitecturas de software modernas. Exploraremos los siguientes temas avanzados:

  • Integración con Bases de Datos: Interactuaremos directamente con bases de datos relacionales como PostgreSQL o MySQL para persistir y consultar datos de forma estructurada, superando las limitaciones de las hojas de cálculo.

  • Colas de Mensajes: Introduciremos el concepto de colas de mensajes (por ejemplo, RabbitMQ o AWS SQS) para desacoplar sistemas y gestionar flujos de trabajo de manera asíncrona, un patrón fundamental en arquitecturas de microservicios.
